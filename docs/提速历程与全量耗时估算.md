# 从初版到现在：提速历程与全量耗时估算

整理更新：2026-11-06；历史分阶段耗时与本轮匹配实验分别列出。

**历史变化：Python版约需几个月 → 编译单核约3天 → 编译4线程约16小时 → 无损树商图约4—6小时；2026-10-24持续负载外推纯核心计算约3.6小时。** 2026-10-30又验证了BFS重排和CPU配置，但独立实验收益不稳定，仍保留原编号＋4线程，见下文更新。

这里的“全量”始终指：对同一张YouTube图的**全部原始源点**计算精确介数，并得到全部原始节点的分数。数据有 **1,134,890个节点、2,987,624条无向边**。下表全量时间均为实测吞吐的外推，YouTube完整全源任务尚未完成。

## 1. 全量需要多久：一张表看变化

| 阶段 | 当时做了什么 | 已实测的工作量与耗时 | 全量耗时估计 |
|---|---|---|---|
| 原Python单核的大图基线 | 接入CSR，但继续使用原Python Brandes内核 | 同8源三轮，内核耗时中位100.46秒 | 代表值约**165天，即5个半月**；早期吞吐波动对应约5—9个月 |
| 编译单核 | Numba本机代码、复用数组、隐式最短路径DAG | 同8源三轮，内核中位1.727秒 | 约**68小时，即2.84天** |
| 编译2线程 | 两个线程计算不同源点 | 同64源三轮，执行/归并中位6.563秒 | 约**32.3小时** |
| 编译4线程 | 四个线程计算不同源点 | 同64源三轮，执行/归并中位3.249秒 | 约**16小时** |
| 无损树商图＋4线程 | 合并外围树对应的重复核心计算，保留端点数量并恢复原图分数 | 同256原始源三轮，工作中位16.08→10.11秒；另做全源权重试算 | 综合不同样本，粗估**4—6小时** |
| 2026-10-24：分组检查点＋持续负载 | 长时间运行、定期保存、校验并续算 | 已提交37,888个核心源组，核心执行累计1044.89秒 | 按当时吞吐，全计划纯核心执行约**3.60小时**；当时建议预留**4—6小时**窗口 |
| 2026-10-30：BFS重排＋CPU配置实验 | 同源比较布局、4/6/8线程及独立2048组确认 | 候选独立配对工作比1.04/1.55/0.78，未稳定胜出 | 本轮负载外推原版约8.21小时、候选约7.88小时；与历史负载不同，**不替换原方案** |

**表中不是多次全量跑完的成绩。** 短任务的加载、校验、编译、保存开销另计；不能把每个短案例的总墙钟简单乘到全量。检查点阶段是更长观测更新了估计，不能解释成“加上检查点又把4—6小时加速到了3.6小时”。10月30日原版吞吐也变慢，说明不同日期的绝对外推受环境影响，不能把8.21与历史3.60直接当作算法退化比较。

初版在Facebook、ca-GrQc等小图上已经有串行和spawn多进程功能。其原始Python图表示在YouTube上没有成功的同协议计时，因此第一行使用“CSR接入后的原Python单核内核”作为可核验的大图基线；没有对未实测的原Python多进程版本编造YouTube全量时间。

## 2. 每次改了什么，为什么有效

### 第一步：CSR紧凑存储——先让几百万条边稳定装进内存

最初读取时会产生较多Python元组、集合、字典和邻接列表。CSR用两组连续数组保存“邻居在哪里、邻居是谁”，并通过只读映射缓存加载，减少对象和数据副本。

这一步主要解决**大图接入与内存问题**。当前图的邻接数组约31.45 MiB，原始ID映射另占8.66 MiB；原Python循环仍然慢，尚无独立对照证明CSR本身带来多少计算提速。

### 第二步：Numba编译——把反复执行的Python循环变成本机数值循环

Brandes对每个源点执行一次BFS，再反向计算最短路径依赖。将这些循环交给Numba编译，同时复用固定类型数组；利用距离标签识别最短路径上的前后关系，省去Python前驱列表。

数学递推保持一致，主要降低执行常数。同8源配对实验的核心加速比中位约**58倍**，短案例整例约**14.8倍**。这是编译、数组复用和隐式DAG的组合收益，不能全部归因于编译一个因素。路径计数可能超出int64时，会在提交贡献前回退到Python任意精度计算。

### 第三步：源级多线程——让多个CPU核心同时分担源点

不同源点的贡献可以独立计算，最后相加。Numba内核释放GIL后，多个线程可真正并行；它们共享只读图，各自保留工作区和累加向量，再归并结果。动态领取小批次，减少线程等待。

同64源、同一组CPU亲和性范围的实验，4线程相对单线程取得约**4倍执行加速**。没有把图拆成小图；每个源仍计算整张图。原计划考虑扩展spawn多进程，实际依据已有nogil内核和内存条件选择了共享图的线程路线。

### 第四步：无损树商图——减少必须重复做的计算

外围树通过唯一锚点连接核心，树内到核心的路径具有可复用结构。将锚点和附着树表示为一个带“原始节点数量”权重的组，在核心执行带权Brandes，再解析恢复树内及锚点的原图贡献。

例如一个锚点连着9个外围节点：核心部分可以由一次源数量权重为10的遍历代表这10个原始源，外围路径贡献另行恢复。**所有原始节点、树边和端点贡献都保留。** 权重表示节点数量，不是边长，也不会直接乘到最短路径条数上。

YouTube需要遍历的核心源组由1,134,890个原始源对应的逐源遍历降为 **470,164组**；每次遍历的核心图为470,164个节点、2,322,898条边。另存664,726个外围节点对应的树边与映射。因此同时减少了“遍历次数”和“每次遍历的状态规模”。

### 第五步：检查点与恢复——让数小时任务可持续完成

每1024个核心源组保存一次贡献，先写贡献文件，最后提交带哈希的清单；重启校验已经完成的组，只继续未提交部分。逐源任务记录按组释放，全部源组完成后才统一恢复原图分数和归一化。

这一步主要降低**中断重算成本和长期内存风险**，不会直接减少Brandes的数学计算量。目前一组约28秒，普通中断通常只需重算最后一个未提交组。已验证1000秒硬中断后的续算，36个历史提交保持不变。

## 3. 全量时间怎样估算

未压缩版本按原始源点数量外推；商图版本按带源数量权重的核心源组外推：

```text
原Python：100.4611秒 / 8源 × 1,134,890源 ≈ 165天
编译单核： 1.7274秒 / 8源 × 1,134,890源 ≈ 68.1小时
编译4线程：3.2492秒 / 64源 × 1,134,890源 ≈ 16.0小时
当前商图：1044.8866秒 / 37,888核心组 × 470,164核心组 ≈ 3.60小时
```

商图全源时，每组的源权重等于该组原始节点数量，目标权重覆盖整个原图。不能再把核心单组时间乘原始节点数，也不能只按未加权的小样本推算。

各阶段源集合、工作量和运行条件不同，**不能把“58倍×4倍×商图倍数”当成实测总加速比**。表格用于理解耗时数量级；长期频率、系统负载、后续整数溢出回退和中断都会改变最终时间。

## 4. 目前真正完成到哪里

截至2026-10-24验收，已保存 **37个检查点、37,888个核心源组，约8.06%**，代表90,087个原始源。按该段吞吐，当时剩余纯核心计算约3.31小时，尚未产出YouTube全源排名。

完整回归245项通过，随后补充的检查点专项共24项通过；两张旧真实图完成全源暂停/恢复对照。YouTube还用未压缩图独立计算首组对应的2289个原始源，全部1,134,890个节点贡献均通过浮点容差核对。这里的精确指计算完整定义，不代表浮点结果逐位相同。

一句话讲给老师：**先降低数据存储成本，再降低每次计算的执行开销，然后用多核分担独立源点，最后利用图结构消除等价的重复计算；检查点保证长任务中断后能够继续。**

2026-10-30更新：核心结构诊断发现最大双连通块仍占核心节点96.15%、边98.80%，进一步BCC分解的结构指标只下降约5.43%，未贸然实现复杂后端。随后实现BFS重排并完成主512组、独立2048组三轮对照，302项回归和两张旧真实图全源核对通过；但候选组合在独立第三轮变慢，保留一次超时及补测，最终继续使用原编号＋4线程。旧8.06%进度完整保留。**优化过程也包括验证不值得采用的方案，而非每次改动都必然提速。** 详情见[本轮实测](RESULTS.md#layout-results)。
