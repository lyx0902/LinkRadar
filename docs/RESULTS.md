## 5. 节点移除：排名是否有结构意义

每个策略从原图重新开始，按原图固定介数、度数或随机排列逐步移除；不每删一个点重算排名。随机采用20个独立可复现排列，每条曲线是同一排列的嵌套前缀。主指标为剩余最大连通分量节点数 / 原始节点数，比例用floor(q*n)得到实际移除数。

ca-GrQc原本有355个分量，所以起点LCC/n=4158/5242≈0.7932，而Facebook起点为1。这种初始差异不能算作节点移除造成的损失。

| 图 | 实际移除k | 实际比例 | 介数策略LCC/n | 度数策略LCC/n | 随机均值LCC/n |
| --- | --- | --- | --- | --- | --- |
| facebook | 807 | 19.980% | 0.178262 | 0.658084 | 0.786321 |
| ca_grqc | 1048 | 19.992% | 0.007631 | 0.006677 | 0.565986 |

Facebook在约20%这一点上，介数策略后的最大分量明显小于度数和随机策略；ca-GrQc在这一末点上反而是度数略强。完整曲线还显示不同删除比例可能有不同差异。因此结论应限定到网络、策略和比例，不能说“介数任何时候都更有效”。随机阴影是10%–90%经验分位范围，不是置信区间。

### 结论

**继续做BCC分解存在结构上的缩减空间，但主要计算仍集中在一个巨型双连通块。建议下一轮优先测试顶点重排和线程配置，暂缓完整BCC数值加速实现。**

最大块保留96.15%的核心节点和98.80%的核心边；按块规模计算的工作量指标只下降约5.43%。这不能支持“进一步BCC分解就能再获得几倍加速或降至分钟级”的预期。它也不是实测收益上限：访存、边界权重、分块复制和归并都会影响实际耗时。

输入为已有无损商图缓存 `data/processed/youtube_csr_treeq/`。原始网络包含1,134,890个节点、2,987,624条无向边，所有原始节点仍由锚点与外围树表示。

|---|---:|
| 核心节点 / 无向边 | 470,164 / 2,322,898 |
| 核心平均度 | 9.881 |
| 核心连通分量 | 1 |
| 割点 | 8,387 |
| 桥 | 2,364 |
| 边块总数（包含单桥二节点块） | 8,935 |
| 含环双连通块 | 6,571 |
| 最大块节点 | 452,060，占核心96.149% |
| 最大块边 | 2,295,072，占核心98.802% |

| 所有桥中，较小侧原始端点数量的最大值 | 83 |

这里的桥只统计仍留在核心中的桥，已经由外围树表示的桥不重复计入。桥两侧数量使用锚点代表的原始节点数量，所以最后一行以原始节点为单位。它说明这些核心桥连接的较小侧仍很小，不能将巨型核心分成规模相近的两个大块。

割点可以出现在多个双连通块中，因此各块节点数会有重复；边则恰好属于一个块。当前块节点数总和479,098，满足 `n + 块数 − 连通分量数`，不能把它误读为新增了原始节点。

### 计算量指标怎样解释

使用与Brandes逐源遍历成本对应的粗指标：

```text
当前核心：active_n × (n + m)            = 1,313,197,202,168
分块后：sum n_i × (n_i + m_i)          = 1,241,868,687,721
排除可解析的单桥块后                  = 1,241,868,673,537
含环块指标 / 当前核心指标              = 0.945683
指标下降                              ≈ 5.43%
```

这只比较结构工作量。它不是已经实现的BCC算法耗时、实测加速比或严格运行时间上下界，不包括块外端点数量、割点分数修正、数据复制、调度和归并。**不据此修改此前约3.6小时的全源核心外推，也不把5.43%写成已获得的提速。**

实际分布是一个极大的块加许多小块，并非大量规模相近的块。进一步优化的主要对象仍是这45万余节点的巨型块。

## BFS 顶点重排方法

### 编号、数量权重和结果怎样保持一致

以固定种子选择BFS起点，记录访问次序；若有多个连通分量或孤立点，继续覆盖全部剩余节点。定义 `new_to_old[new]=old`，其逆为 `old_to_new[old]=new`。

```text
新邻接：old_to_new[旧邻居]
新目标数量：mass_new[new] = mass_old[new_to_old[new]]
新源数量：source_counts_new[new] = source_counts_old[new_to_old[new]]
源点：new_source = old_to_new[old_source]
还原核心贡献：K_old[old] = K_new[old_to_new[old]]
```

还原后的核心贡献再交给原有外围树恢复函数，输出仍按原始节点顺序排列。BFS只改变编号和数组访问顺序，不删除节点/边，不修改数量权重或最短路径长度。

独立布局缓存使用0..n−1作为内部ID；原始节点ID仍由旧商图和映射解释。布局物理图有自己的指纹，同时绑定原图和旧核心指纹。缓存创建/加载时逐项核对排列、逆映射、质量与度数，并将全部重排边映射回旧编号，与旧核心CSR完整比较。

两种布局均保存为独立只读CSR缓存：natural为恒等映射，bfs为BFS映射；不覆盖原缓存。两者采用相同加载、校验和计时路径。

## 反向依赖系数复用：原理与 64 源组实验

2026-11-02。实验结论：**候选内核数值对照通过，但 3 轮中有 1 轮变慢，不满足本轮稳定收益筛选，暂不接入正式检查点链路。** 只测试了 64 个核心源组，结论不代表所有图和机器上的表现。

### 现有计算与候选公式

在无权核心图中，从源组 r 做 BFS，得到源到节点 v 的最短路径条数 σ(v)。反向按距离从远到近计算依赖，M(w) 是 w 所代表的原始目标节点数量：

$$D(v)=\sum_{w:d(w)=d(v)+1}\frac{\sigma(v)}{\sigma(w)}(M(w)+D(w)).$$

同一个后继 w 可能被多个前驱使用，实验方案在算出 D(w) 后保存系数

$$q(w)=\frac{M(w)+D(w)}{\sigma(w)},\qquad D(v)=\sum_{w:d(w)=d(v)+1}\sigma(v)q(w).$$

因为反向遍历先处理更远的节点，访问 w 时 q(w) 已经算好。除法从符合条件的边上重复执行，变为每个已访问节点一次；但另需访问系数数组，能否提速取决于图结构、CPU 和内存行为，不能由除法次数直接推断。

例如 σ(v)=2、σ(w)=4、M(w)+D(w)=10，原项为 (2/4)×10=5；候选先保存 q(w)=10/4=2.5，再算 2×2.5=5。若另一个前驱也连接 w，它可以复用 2.5。数学表达式等价，浮点运算顺序不同，故结果按容差核对而不是要求逐位相同。

### 实现边界

候选位于 `src/parallel_bc/quotient_coeff_experiment.py`，采用 Numba、`nogil=True`、`fastmath=False`，与原实现一样保存 `delta` 用于最终累加。每个线程另有一个 float64 系数数组：YouTube 核心每线程 3,761,312 字节（约 3.59 MiB），4 线程约 14.35 MiB。现有调度器统计的 workspace_bytes 只包含原工作区，不包含这个额外数组；以上额外内存单独计入。

BFS 中保留 int64 路径数溢出检查，溢出时完整重算该源的 Python 大整数依赖，成功后才提交。候选对非有限系数也会停止；极端数值情况下计算顺序改变可能产生不同的浮点行为，不能声称逐位等价。

### 真实图对照

使用 YouTube 原编号商图，种子 46 的 64 个核心源组，代表 122 个原始源；目标数量权重始终覆盖全图。原版和候选均使用同源、4 线程、批大小 4、进程亲和性 `[0,2,4,6]`。完成 JIT 预热后交替次序，共三轮。计时为线程执行与归约，不包括商图加载、编译、恢复和进程启动。
