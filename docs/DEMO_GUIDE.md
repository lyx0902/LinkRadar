# LinkRadar 展示讲稿与操作路线

先读[项目整体说明](PROJECT_GUIDE.md)，再用本篇排练。这里提供约8分钟的参考结构，不是实际演讲计时记录。数字和图均来自[当前结果报告](RESULTS.md)。

## 1. 展示前只准备四样东西

1. 打开[整体流程图](figures/pipeline.svg)与[并行分工图](figures/parallel_sources.svg)。
2. 打开[Top10对照图](node_insights/top10_comparison.png)、[失效曲线](../results/20261023T054258_364875Z/figures/robustness.png)和[配对复测图](node_insights/facebook_paired.png)。
3. 在项目根目录运行下面的本地服务器，浏览器访问 `http://127.0.0.1:8765/`。它只服务本机文件，不是外网部署；终端保持运行，结束时Ctrl+C。
4. 备好[当前结果报告](RESULTS.md)和[节点CSV](node_insights/facebook_top10.csv)，网络或页面异常时仍可展示静态图与数值。

```powershell
.\.venv\Scripts\python.exe -m http.server 8765 --bind 127.0.0.1 --directory web/linkradar/dist
```

本地网页不用外网、npm、数据库。应用内浏览器限制file协议，本项目实际通过本地HTTP检查；不要把尚未验证的浏览器入口当成现场唯一方案。

## 2. 约8分钟的讲解路线

### 第1分钟：先讲任务，不先列库名

建议说：

> 我的输入是一张“谁和谁相连”的网络。我想找出哪些节点经常承担最短路径中转，再研究这项计算如何使用多个CPU进程完成。项目既研究网络结构，也研究并行计算的收益和代价。

指着整体流程图，从原始边列表讲到清洗、计算、核验、实验和网页。强调输出不只有一个前十榜单，还包括所有节点分数、运行日志、原始计时与结构失效结果。

### 第2分钟：用小图说明“介数”

展示[整体说明中的五节点例子](PROJECT_GUIDE.md)：S到T有两条等长最短路径，经A与B各走一条，因此各分1/2份；不能随便挑其中一条。Brandes通过路径计数与反向累计复用计算，再把每个节点都作为起点。

建议说：

> 度数看“直接连了多少人”，介数看“节点对之间的最短路是否经过这个位置”。它不是社交地位或学术贡献评分。

不必现场推导完整递推公式，想深入的同学可以看[并行计算说明](PARALLEL_COMPUTING.md)。

### 第3–4分钟：明确指出并行的位置

指着并行分工图说：

> 每个起点的单源贡献可独立计算。我让多个进程读取同一张完整图，各自计算不同起点，在自己的分数数组中累计。最后每个进程回传一次总向量，由主进程相加，统一做无向修正和归一化。拆的是起点任务，不是图的连接。

用八起点、B=2、p=2的表说明静态固定交替分配与动态空闲领取的区别。两种模式使用相同批次和相同单源内核；动态不保证更快。

然后展示[实际worker记录](../results/20261023T061912_984947Z_facebook_paired/workers_0_2.json)：四个不同PID分别处理1024、1024、967、1024个起点，合计4039。说明这些PID是当次历史运行，不是此刻仍在计算。当前保留的真实图实验没有记录逐批时间线，展示时用这份worker日志解释实际起点分工。

### 第5分钟：用正确性和计时说明“不是只创建几个进程”

建议说：

> 三种方式最后应该得到同一套全图分数。项目对所有节点的raw和normalized与NetworkX核对，并检查每个起点不重不漏。性能统计同时算包含启动的total和排除启动清理的steady，不能只展示好看的一个数。

展示两个分开的结果：ca-GrQc首轮serial约16.25s、四进程静态约6.22s，观察总加速约2.61；Facebook后续固定四个逻辑CPU的配对复测，serial约132.54s、dynamic(p=1)约127.56s、dynamic(p=4)约77.31s，观察比值约1.71。

补一句：

> 首轮Facebook曾出现单工作进程也快两倍的异常，因此没有把那轮四进程3.36倍当成可靠结论，而是保留记录并重新配对测量。新实验也有波动，只是本机本轮观察，不是稳定倍数承诺。

### 第6分钟：在网页上讲一个具体节点

1. 选择Facebook，展示4039节点、88234边与介数Top10。
2. 点击58号柱条，读出：度数12，度排名2918，介数第9。解释它的中转排名不靠最多的直接连接。
3. 点1085号：介数第5，但不是割点，说明高介数不等于单点断裂。
4. 切换ca-GrQc，确认5242节点、14484边、355个分量，排名首位为原始ID13801。
5. 选一个局部图节点看参数，说明局部图仅截取最多120个节点辅助解释，分数仍在完整原图计算。布局远近没有现实距离含义。

如果想示范参数可复核，可用原始ID搜索、切换到度排名、展示全部节点分页，再下载CSV。无需把全部功能都点一遍。

### 第7分钟：用失效实验检验结构作用

打开“失效实验”页，解释主指标是剩余最大连通分量 / 原始节点数。

> 我按原始图排名依次删节点，不是每删一次就重新排名。介数、度数与20次随机排列从同一张原图开始。Facebook在约20%这一点上，LCC/n约为0.178、0.658、0.786，介数策略造成的破坏更大。ca-GrQc在同一比例的末点上度数略强，因此不能说介数永远更好。

提醒：ca-GrQc原本不连通，起点约0.7932不是1；随机阴影是经验分位范围，不是置信区间，也不是现实用户流失预测。

### 第8分钟：收束到已经实现的东西和边界

建议说：

> 本项目完成了真实数据处理、同核心精确串并行、正确性核对、预算和日志、真实性能实验、固定排名失效，以及可交互展示。它说明了“怎样把独立起点任务并行化并验证结果”，也说明并行不是进程越多必然越快。下一步可继续真实图批次扫描与更充分的重复测量，而不是先把尚未测过的优势写成结论。

个人贡献按实际协作说明，AI辅助实现与自己的方案理解、数据准备、实验判断分开交代；不需要为了展示声称全部代码都是独立手写。

## 3. 课堂常见追问

| 问题 | 可直接回答 |
|---|---|
| 并行在哪里？ | 外层全部起点的循环。多个进程同时做不同起点，单源内部仍先BFS后反向累计。 |
| 把图切成四份了吗？ | 没有。每个进程有同一完整图的副本，保留所有跨群体路径。 |
| 为什么不会重复计数？ | 起点批次严格分割全部节点，实际批次与起点数量都检查；无向两方向重复在最终统一除以2。 |
| 为什么用多进程？ | 当前普通Python内核通过独立进程获得多核并发执行的条件；实际由系统调度，仍有启动、内存和通信成本。 |
| p=4是不是只有四个系统进程？ | p只计四个计算工作进程，还可能有主进程、预算监管和系统辅助进程。 |
| 动态是不是一定快？ | 不是。动态可让空闲进程继续取任务，也增加管理开销；必须同图同p同B实测。 |
| 四进程为什么不是四倍？ | 存在不可平分的启动、传图、通信、归并，任务分布与CPU调度也有影响；四个逻辑CPU也不一定是四个物理核。 |
| 为什么一边用NetworkX一边说自写算法？ | 介数主体是自写内核；NetworkX用作独立全节点参照，也用于生成图、割点和部分结构分析。 |
| 高介数就是最重要的人吗？ | 只能称当前匿名拓扑中最短路径中转作用强，不能推断身份、社会地位或学术贡献。 |
| 介数高的删掉一定断吗？ | 不一定；有替代路径时它可以不是割点。多个节点依排名逐步删除的失效实验又是另一种问题。 |
| 网页在并行计算吗？ | 网页展示Python算好的结果，页面切换不会重新跑Brandes。要从网页提交长任务，需要另外的后端API和任务队列。 |
| 文件不大为什么算这么久？ | 显示几千个节点的结果很轻量，但全起点算法重复遍历图，计算量远大于只读取一次文件。 |
| 结果怎样查证？ | 数据指纹、全节点CSV、validation、原始计时、PID与任务日志、manifest都能回溯，入口在RESULTS.md。 |

## 4. 可复制命令：区分看结果和重跑实验

以下命令从项目根目录执行。日常展示使用已有结果即可；不要为了打开网页而重新跑二三十分钟的真实图实验。

### 短离线全流程与测试

```powershell
.\.venv\Scripts\python.exe -m parallel_bc --help
.\.venv\Scripts\python.exe -m parallel_bc demo --profile smoke
.\.venv\Scripts\python.exe -m pytest -q
```

早期smoke产物已清理。主动执行此命令会重新生成合成数据与结果目录，不依赖真实文件或网络。它演示真实spawn与全流程，但不代表真实图性能。

### 手工导入真实数据

```powershell
.\.venv\Scripts\python.exe -m parallel_bc data import --dataset facebook --path "data\raw\facebook\facebook_combined.txt.gz"
.\.venv\Scripts\python.exe -m parallel_bc data import --dataset ca_grqc --path "data\raw\ca_grqc\ca-GrQc.txt"
```

当前缓存已存在，只有需要重新准备数据时才执行。txt/txt.gz均支持，文件实际位置不同则改--path。import直接读取本地文件，prepare还可能触发注册URL的下载。

### 真实图研究与复测：较长运行，按预算执行

```powershell
.\.venv\Scripts\python.exe -m parallel_bc benchmark --config configs/real_quick.yaml
.\.venv\Scripts\python.exe scripts/paired_baseline.py
```

前者两图、p=1/2/4、B=128、三次重复、随机失效20次，计算预算1800秒；后者仅Facebook，固定4个可用逻辑CPU，一次全图热身与9个正式案例，默认1200秒预算。机器状态不同可能触及预算；只能报告实际完成范围。

合成规模、粒度与时间线分别见 `configs/quick.yaml`、`configs/granularity.yaml`、`configs/diagnostic.yaml`。full必须显式启动，本项目当前没有执行其完整矩阵。

### 重新导出参数图与网页数据：不重算完整介数

```powershell
.\.venv\Scripts\python.exe scripts/export_node_insights.py --reference-run results/20261023T054258_364875Z --paired-run results/20261023T061912_984947Z_facebook_paired
```

会检查图指纹与分数覆盖，重生成node_insights下的自动参数附件与网页数据；当前四份主文档不会被覆盖。不要在自动附件末尾手工积累独有结论，重要解释应维护在RESULTS.md中。

### 自动阶段性摘要与文档检查

```powershell
.\.venv\Scripts\python.exe scripts/real_research_summary.py results/20261023T054258_364875Z
.\.venv\Scripts\python.exe scripts/check_docs.py
```

第一个只生成 `results/summaries/` 下的真实图摘要与索引，不替代当前主说明，也不重跑实验。第二个检查本地Markdown链接和流程图SVG的XML格式。
