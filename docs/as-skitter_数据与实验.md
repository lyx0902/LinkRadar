# as-skitter 数据与实验

## 全量数据处理时间开销

**as-skitter 尚未完成全源计算。** 按当前主链路、8 线程和每块 2,048 个核心源组估计，核心计算约 **25 小时**；安排时建议预留 **30 小时以上**，实际可能更长。以下是同机试算的线性外推，不是全量实测，也不是严格的时间上下界。

| 8 线程样本 | 实测核心执行与归并 | 外推 1,464,020 个核心源组 |
| --- | ---: | ---: |
| 2,048 组，seed 46 | 109.132 秒 | 约 21.7 小时 |
| 2,048 组，seed 47 | 142.858 秒 | 约 28.4 小时 |

两次外推的简单平均约 25.0 小时。两轮系统状态和运行顺序不同，无法仅凭记录确定差异原因。各样本只覆盖约 0.14% 的核心源组；长时间负载、散热、内存、溢出回退、重复加载和中断重算都可能影响最终耗时。按 2,048 组/块预计提交 **715 次检查点**；每块核心耗时可参考上述 109–143 秒，但运行中会波动。

作为另一种粗略参考，YouTube 全源任务 8 线程分两次会话完成，两次监督墙钟合计 **9,037 秒，约 2 小时 30 分 37 秒**，不含会话间停顿。以“源组数 × 核心节点及边规模”按图规模缩放，as-skitter 约为 **34.5 小时**；这是跨图结构代理估计，不是性能上限。[YouTube 全量报告](Youtube全量处理报告.md)记录了该次运行。

## 0. 结论摘要

保留现有 **CSR → 树商图 → DAG 边记录 → 源组级线程并行 → 双累计快照 → 原图恢复**主链路。树商图仍是无损的，但 as-skitter 核心图保留了原图大部分节点和边，因此降规模的效果弱于 YouTube。已有图重排和双源批量原型实验均未进入默认全量链路。

| 方向 | 简要结论 | 实施难度 |
| --- | --- | --- |
| 线程与运行环境 | 2,048 组同源单次测量中，8 线程比 4 线程快约 1.23 倍；12 线程比 8 线程快约 4.9%，但内存更高。可继续使用 8 线程并关注可用内存，不能仅凭单轮认定最优线程数。 | 低 |
| BFS 节点重排 | 两轮 1,024 组 A/B 的核心工作加速比分别为 1.057、1.348，端到端比为 0.919、1.228；波动明显，暂不采用。 | 中；需复测并保持节点映射和检查点兼容 |
| 内核微调 | 可研究工作区复用、调度粒度或数组类型；目前没有证明能够显著加速全量任务。 | 低到中；需数值、内存和端到端对照 |
| MS-BFS / 批量 Brandes | 双源原型三轮均慢于 DAG 基线；位图等完整方法尚未实现，不能据此否定所有批量方法。 | 高；须处理逐源路径数、带权恢复及内存 |
| BCC/BADIOS 结构分解 | 最大双连通块含 98.57% 核心节点、99.70% 核心边；既有工作量代理仅下降约 1.8%，不是实测加速比。 | 高；块间权重及贡献恢复复杂 |
| degree-2 路径收缩 | 需要保持路径长度、多条最短路径及原节点贡献；此前约 4.2% 的“上界”未经严格推导，不作为确定结论。 | 高 |
| pull-based BFS | 可能减少部分大 frontier 的扫描，但 Brandes 仍须正确处理路径数与反向依赖；尚无本项目实测。 | 高 |
| GPU 或采样近似 | GPU 需要对应硬件与重新实现；采样会改变结果语义，需要单独评估误差。两者均没有本项目的全量收益实测。 | 高；采样还需重新定义准确性 |

## 数据与准备

数据是用户手工下载的 SNAP 格式 `data/raw/as-skitter/as-skitter.txt.gz`，按无权、无向图处理。节点 ID 从 0 开始。

| 项目 | 实际数据 |
| --- | ---: |
| 原图节点 / 无向边 | 1,696,415 / 11,095,298 |
| 连通分量 / 最大分量节点 | 756 / 1,694,616 |
| 商图核心节点 / 无向边 | 1,464,757 / 10,863,640 |
| 外围树节点 | 231,658 |
| 需要遍历的核心源组 | 1,464,020 |
| 纯树分量锚点 / 对应原始源质量 | 737 / 1,698 |

737 个无核心边锚点无需核心遍历，其原始源贡献通过解析恢复；其余源点由核心源组权重表示，最终再恢复全部原图节点。核心节点和边分别保留了原图约 86.3% 和 97.9%。

本地边表覆盖所有 1,696,415 个 ID，构图结果无孤立点；文件头关于度为 0 节点的注释与本地边表不一致，本次以实际边表和 CSR 元数据为准。当前 SNAP 解析不从头部补入未出现在边表中的孤立点，换数据时应另行核验。

曾在本机运行以下准备命令，CSR 和商图准备分别耗时 **30.74 秒、20.99 秒**；两份缓存合计约 **266.7 MiB**。`--reserve-gib 0.25` 是当时内存紧张下的实验设置，运行时应结合当前可用内存调整。

```powershell
.\.venv\Scripts\python.exe -m parallel_bc data prepare-csr `
  --dataset as-skitter --path data/raw/as-skitter/as-skitter.txt.gz `
  --format snap --timeout 900 --reserve-gib 0.25

.\.venv\Scripts\python.exe -m parallel_bc data prepare-quotient `
  --dataset as-skitter_csr --timeout 900 --reserve-gib 0.25
```

已有缓存位于 `data/processed/as-skitter_csr/` 和 `data/processed/as-skitter_csr_treeq/`。

## 全量运行与结果

使用已准备好的缓存，新建 8 线程任务的示例：

```powershell
.\.venv\Scripts\python.exe -m parallel_bc quotient-run `
  --dataset as-skitter_csr --run-dir results/as_skitter_full `
  --threads 8 --batch-size 4 --chunk-size 2048 --seed 45 `
  --timeout 3600 --reserve-gib 1 `
  --cpu-affinity 0 2 4 6 8 9 10 11
```

`--timeout 3600` 是单次会话的时间上限；需要继续时使用同一命令、同一运行目录和参数，加上 `--resume`。续算会核对图、数值代码、依赖、源计划、线程及分块配置等身份信息；未提交的块可能重算。每完成一块，终端输出已提交进度；运行目录中的 `manifest.json` 记录 `completed_core_groups`。详见[当前链路与检查点](Pipeline_and_Checkpoints.md)。

8 线程试算曾记录约 **1,692 MiB** 进程私有内存峰值，其中一次系统最低可用内存约 **850 MiB**；这是当时的采样值，不保证未来运行足够。建议先释放内存并保留合理余量。缓存外，双快照、源计划和最终结果数组预计共约 67 MiB，另有少量清单和临时文件。

完成前的 `snapshot_A.npy` / `snapshot_B.npy` 是部分核心累计贡献，不能当成全图排名。全源完成后才生成 `contributions.npy`、`bc_raw.npy` 和 `bc_normalized.npy`，节点顺序与商图缓存中的原始节点 ID 顺序对应；`exact_all_sources=true` 表示全源覆盖，`float64` 仍存在舍入误差。

## 已做的实验

实验环境为 Windows 11、Intel Core i5-13500H、约 15.53 GiB 内存。所有 as-skitter 结果都是部分源组试算，没有完成全图介数计算。

- **规模与线程试算**：64、512、2,048 组及多线程配置验证了现有链路可运行；8 线程的两次 2,048 组结果及外推见文首。试算中没有触发路径数溢出回退，不能保证全源不会触发。
- **结构诊断**：最大双连通块集中，BCC 诊断得到的工作量代理下降约 1.8%，没有实现完整 BCC 数值优化。
- **BFS 图重排**：同一批 1,024 源组、8 线程、两轮交替对照；核心工作比 1.057 / 1.348，端到端比 0.919 / 1.228。恢复到原图的部分贡献通过容差比较，但收益不稳定，未接入主链路。
- **双源批量 Brandes**：同一批 64 源组、4 个逻辑 CPU，单源 DAG 使用 4 个线程，双源原型使用 2 个线程。三轮 DAG/双源工作时间比分别为 **0.322 / 0.402 / 0.426**，中位数 **0.402×**；原型更慢。全部原图节点的部分贡献通过 `atol=1e-8, rtol=1e-10` 对照，最大绝对差约 `1.863e-9`。原型没有实现位图 frontier、SIMD 或 DAG 边记录。
- **双源分阶段诊断**：同样 64 组中，按两源分别扫描的邻接项计，约 **21.92%** 可在同层共享；双源线程阶段墙钟时间之和中，反向阶段占约 **53.04%**。这不是相对生产 DAG 的总扫描减少率或加速比；诊断只支持继续关注反向阶段，不能证明唯一瓶颈。本轮进程内存峰值采样无效，不能用于判断内存占用。

主要原始记录保存在本地忽略目录：`results/as_skitter_pilot_2048_t8_20261110/`、`results/as_skitter_pilot_2048_t8_seed47_20261110/`、`results/20261110T044852Z_as_skitter_layout_dag_ab/`、`results/batch2_as_skitter_64_20261113T021855_163179Z/` 和 `results/batch2_diagnostic_64_20261113T023523_991773Z/`。这些本地产物未必随仓库发布。

as-skitter 的核心节点全源结果尚不存在，也没有对该图核心节点的全源结果进行独立算法逐点验证；小图和部分源组对照不等同于全源证明。算法和恢复方法见 [Algorithm.md](Algorithm.md)、[图优化](Graph_Optimization.md)。
