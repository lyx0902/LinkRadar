# LinkRadar 交互式网络分析报告

这是 LinkRadar 的静态网页，用于浏览四张真实网络的介数中心性结果、节点失效实验和计算方法。网页展示已经计算并导出的数据，交互操作在浏览器中完成。

[在线访问](https://lyx0902.github.io/LinkRadar/) · [项目主页](../../README.md) · [实验结果](../../docs/RESULTS.md)

## 浏览网页

从项目根目录启动本地 HTTP 服务：

```powershell
.\.venv\Scripts\python.exe -m http.server 8765 --bind 127.0.0.1 --directory web/linkradar/dist
```

浏览器打开 <http://127.0.0.1:8765/>，结束时在终端按 `Ctrl+C`。也可以直接访问上面的在线页面。

侧边栏提供七个分栏。01—03 页顶部可以在 Facebook、ca-GrQc、YouTube 和 as-skitter 之间切换，查看节点数、边数、连通分量数及最大连通分量占比；04—06 与 0Z 页介绍通用算法、优化、整体结果和实验跟踪，不显示网络选择器。侧边栏底部的 GitHub 链接可以打开项目仓库。

### 01 关键节点

从全图介数中心性出发，查看网络中承担最短路径中转作用的节点：

- **全图介数 Top 10**：用柱形图展示排名前十的节点；点击柱条可查看对应节点。
- **节点参数**：展示原始 ID、raw 和归一化介数、度数及度排名、所在分量大小和割点状态。
- **局部网络**：展示介数前十节点及其部分邻居，支持点击节点、拖动和缩放。局部图用于观察连接关系，节点分数来自完整原图。
- **节点排名与参数**：按原始 ID 筛选、按介数或度数排序、分页查看全部节点，并下载 Top 10 或全节点 CSV。

节点 ID 为数据集中的原始编号。大图全节点 CSV 由浏览器生成，下载时会占用额外内存。

### 02 失效实验

比较按原图介数排名、原图度数排名和随机顺序移除节点后，网络连通结构如何变化。曲线的横轴是移除节点占原图节点数的比例，纵轴是剩余最大连通分量占原图节点数的比例；随机曲线为 20 次独立排列的均值，阴影为 10%—90% 经验分位范围。排名在原图上确定，移除过程中不重新计算。

页面还展示度数与归一化介数的散点图，帮助比较直接连接数量和路径中转作用。Facebook、ca-GrQc 展示全图节点；YouTube 和 as-skitter 的散点各抽样 30,000 个节点，并标出全图介数 Top 10。切换网络会同步更新图表和数值。

### 03 实验信息

按所选网络展示已有实验配置和计时记录：

- **Facebook、ca-GrQc**：当前优化链路 4 线程全源单次运行的配置与耗时，以及原 Python 链路的首轮计时、配对复测图表和来源信息。
- **YouTube、as-skitter**：全量运行的软硬件环境、图规模、线程数、批次及检查点配置，以及现存会话的状态与耗时。

这里展示的是已保存的结果；切换页面、筛选或选择网络不会重新执行全图计算。不同数据集的计时范围与实验配置请结合页面说明阅读。

### 04 Brandes算法

介绍无权无向图、介数中心性和归一化的定义，以及 Brandes 算法如何通过 BFS 统计最短路径、再按逆序累计节点依赖。页面包括：

- **五节点最短路径示例**：切换端点对和观察节点，查看等长路径及其贡献份额。
- **Brandes 分步演示**：固定一个起点，逐步查看距离、路径数、前驱和依赖值的变化。
- **并行与实验指标**：介绍串行、静态分批、动态分批，及最大连通分量、计时、加速比与误差等概念。
- **术语速查**：搜索节点、前驱、LCC、批次等术语。

真实图的示例数据随前 01—03 页选定的网络变化。教学交互只使用五节点示例，公式通过浏览器原生 MathML 展示。

### 05 优化链路

从两条路径说明项目如何完成全源介数计算：原图路径使用 Python Brandes，优化路径结合 CSR、树商图和编译内核；四张图均已在优化路径完成全源计算。页面分别介绍六个环节的原理与作用：

1. **CSR 压缩数组**：紧凑保存邻接关系，便于遍历和共享。
2. **无损外围树商图**：将外围树对应的源点按锚点分组，并保留恢复原图结果所需的结构信息。
3. **Numba 数值内核**：编译计算热点，复用数值数组。
4. **源组级线程并行**：让多个线程处理独立源组，完成后归并局部贡献。
5. **最短路径边记录**：在正向 BFS 中记录有效后继边，减少反向累积的邻边扫描。
6. **双累计快照**：分块保存核心累计贡献，支持长任务中断后续算。

### 06 总结

汇总四张图的节点数、边数、处理链路和计算会话监督墙钟：Facebook / ca-GrQc 的 4 线程单次运行分别为 2.172 / 1.528 秒，YouTube / as-skitter 为现存会话之和。Facebook 和 ca-GrQc 行同时展示历史 Python 4 进程复测中位数 77.31 / 20.95 秒，以及除以新链路时间得到的约 35.59× / 13.71× 历史比值；YouTube 行展示早期链路的外推耗时和估算比值。小图新旧记录的计时范围、重复次数和运行条件不同，历史比值仅供参考。表格下方结合社交关系、作者合作、在线社区和互联网拓扑，说明高介数节点可以为社群连接、合作网络和拓扑运维等分析提供哪些线索。

## 数据与结果说明

- 网页使用已导出的全源介数结果。全源指覆盖所有原始源点；数值贡献使用 `float64`。
- Facebook 和 ca-GrQc 的基础数据包含在 `dist/assets/data.js` 中。YouTube 和 as-skitter 的全节点二进制资源首次选中对应网络时通过 HTTP 加载，大小分别约 34.6 MiB 和 58.2 MiB；建议通过本地 HTTP 服务或 GitHub Pages 浏览。
- Facebook、ca-GrQc 的新链路全节点结果与此前通过 NetworkX 对照的 Python 分数在容差内一致；此次没有重新运行 NetworkX。小图耗时是使用已有编译缓存的单次会话记录，不包含独立的 CSR 和商图准备。
- YouTube 全量任务的两次会话监督墙钟合计约 **2 小时 30 分 37 秒**，不含会话间停顿；as-skitter 四份现存会话记录合计约 **13 小时 36 分 31 秒**，不含会话间停顿，人工中断可能没有完整会话记录。
- 两张大图的源覆盖和结果文件哈希已经核验；YouTube 外围树节点通过结构公式核对。as-skitter 的 755 个非最大连通分量与 NetworkX 全源对照通过。两图最大连通分量的核心全源结果尚未用另一套算法独立逐点重算。
- as-skitter 结果以实际导入的边表和缓存为准；原文件头提到的零度节点没有从头部自动补入。

详细记录见 [YouTube 全量报告](../../docs/Youtube全量处理报告.md)和 [as-skitter 全量报告](../../docs/as-skitter全量处理报告.md)。

## 网页文件与数据更新

`dist/` 是发布目录：`index.html` 定义页面结构，`app.css` 定义样式，`app.js` 处理主要交互，`theory.js` 实现教学交互；`youtube.js`、`as-skitter.js` 和 `assets/` 中的文件提供相应网络的数据与展示支持。静态页面不需要 npm、数据库或在线脚本依赖。

以下导出操作需要本地已有相应实验结果和数据；它们不是浏览网页的前置步骤。Facebook 和 ca-GrQc 可从项目根目录执行：

```powershell
.\.venv\Scripts\python.exe scripts/export_node_insights.py --reference-run results/20261023T054258_364875Z --paired-run results/20261023T061912_984947Z_facebook_paired --paired-run results/20261023T090440_116909Z_ca_grqc_paired
```

`--paired-run` 可重复指定；页面只展示与当前网络图指纹匹配的复测结果。YouTube 和 as-skitter 使用各自的导出脚本：

```powershell
.\.venv\Scripts\python.exe -B scripts/export_youtube_web.py
.\.venv\Scripts\python.exe -B scripts/export_as_skitter_web.py
```

两张大图的导出需要对应的全量结果和本地缓存；as-skitter 还需要已有的失效实验结果。导出脚本检查相关输入并生成网页资源，不重新计算全图介数。修改图数据后，应先完成相应计算与验证，再重新导出。

## 发布

[GitHub Pages 工作流](../../.github/workflows/pages.yml)发布 `web/linkradar/dist/` 中的静态文件，不运行 Python 实验。仓库 Pages 的发布来源设为 GitHub Actions 后，推送到 `master` 且改动涉及发布目录或该工作流时会触发部署；也可以在 Actions 中手动运行 **Deploy LinkRadar to GitHub Pages**。提交和推送网页资源后，等待工作流完成，再检查线上页面。
